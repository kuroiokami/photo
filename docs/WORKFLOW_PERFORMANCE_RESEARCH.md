# Faster browsing, culling and ingest

Research date: 2026-10-21. Code reviewed at `0cbe1b1`. This is a prioritized research and experiment plan, not implemented functionality or a new performance claim. Existing measurements remain in [PERFORMANCE.md](PERFORMANCE.md); the implemented cache design is [ADR 0025](decisions/0025-thumbnail-cache-tiers.md).

Current follow-up: [RAWviewer, RawSpeed and Geeqie source review](OPEN_SOURCE_PERFORMANCE_REVIEW.md) (2026-10-26) records pinned sources and ranked unimplemented experiments. The dated baseline below is historical: bounded background thumbnail-cache writes, batched initial indexing and later observation/selection improvements have since shipped. Check [the tracker](../PROJECT_STATUS.md) and [implementation checklist](PERFORMANCE_BACKLOG.md) before treating an older proposal as open.

## Optimize the photographer's next useful action

Measure opening a folder to the first visible, decision-ready photo; moving to the next useful preview; requesting to receiving genuine focus detail; applying a decision to seeing it acknowledged; and starting an ingest to the first verified, captioned deliverable. Total copy throughput matters alongside those interaction delays. A fast thumbnail microbenchmark alone does not establish a fast culling workflow.

Photo already has embedded-only RAW browsing, separate thumbnail/Fit/detail workers, lazy grids, bounded RAM/disk thumbnails, selected-first metadata/decision loading, immediate decisions with queued persistence, comparison, pre-copy review, selective copying and verified ingest arrivals. Preserve these. The opportunities below go beyond those existing features.

## Ranked implementation candidates

### 1. Measure real interactions and reduce unnecessary UI updates

**First chunk; high confidence in the need, gains unmeasured.** Add local, filename-free signposts for folder inventory, first preview, decision readiness, queue wait, source decode, cache read/write, metadata publication, decision application/local commit/XMP completion, focus region/full detail and verified family arrival. Record requested-versus-displayed identity so a responsive screen cannot hide a stale-image error. Use Instruments SwiftUI, Time Profiler and Hitches together in release builds. No telemetry upload.

`WorkspaceState.indexPhotos` changes metadata and progress after individual reads. `loadDecision` also updates several observed dictionaries/sets per image. `WorkspaceView.thumbnail` reads collection-wide selection/decision/metadata state. These are credible sources of broad invalidation, not proof that every cell redraws every time. Profile cause/effect before changing the model. Experiment with per-photo observable presentation state, cached display strings and batched background publication every roughly 50–100 ms, while publishing selected-photo results immediately. Preserve stable tile identity and the existing non-observable geometry holder.

Separate a photo becoming actionable from completion of a folder-wide index. Already-loaded decisions must stay usable; unknown external flags must not be guessed. EXIF/rating sorts and filters need accurate completion semantics, stable selection and explicit progress. Do not introduce repeated background grid reshuffling.

**Acceptance:** measured input-to-feedback, actual frame/hitch traces and update counts before/after on identical runs, including concurrent metadata loading, saves, ingest and marquee selection. No regression in decision/filter/Undo correctness.

### 2. Add a bounded foreground-first scheduler and nearby preview preparation

**Second chunk; likely important for cold browsing.** Separate demand into selected Fit/explicit focus, visible thumbnails, nearby candidates and optional background work. Deduplicate by source stamp, session and size. Cancel obsolete queued jobs on selection/direction/folder changes; reject stale completion. Do not let an old prefetch request reset a newer cache session.

Begin experiments with only the next one or two Fit previews in the travel direction, plus a small thumbnail margin around the viewport. Use a byte budget as well as a job count. Start after foreground work settles; pause speculative work during rapid scrolling, pressure or active same-device copying. Test one worker first on cards/HDDs/network storage and small bounded pools on SSDs. Volume capability is a hint; observed queue wait/throughput determines tuning. No whole-folder RAW/detail pre-render by default.

Separate actors do not isolate physical I/O: thumbnails, EXIF, XMP and copying can contend on the same card. A shared per-volume coordinator is more useful than indiscriminately increasing threads. ImageIO/Core Image calls already in progress may be uninterruptible; cancellation drops queued work and later stages, not necessarily the current decode.

**Acceptance:** foreground p95/p99 latency and wasted decode bytes improve under sequential/reverse/random navigation and concurrent ingest; throughput/energy/RSS stay within agreed bounds. Prefetch must earn its CPU, I/O and memory cost.

### 3. Remove cache writing from the time to display a cold thumbnail

At the `0cbe1b1` baseline, `ImagePipeline.preview` encoded/wrote PNG before returning a cold result. Bounded background writes have since shipped; the remaining codec/pressure experiments below are still proposals. The existing benchmark measured 28–31% additional initial population time with disk caching. Publish the decoded image first; evaluate a bounded, best-effort cache-writer queue that can drop obsolete writes under pressure. Recheck source stamps at actual write time and retain atomic records, corrupt-cache recovery and clear-generation behavior.

Compare current lossless PNG with a measured generation-cost threshold and a faster lossless representation. Lossy JPEG/HEIF would need explicit quality/color/alpha tests and must never supply genuine focus detail. Do not change the codec purely because it saves disk space. Cache-writer backlog is decoded image memory and must be included in the budget. Pressure-driven eviction should release thumbnails/speculation before active inspection; avoid simply raising per-window limits again.

**Acceptance:** lower first-display latency without degrading return visits, color, source labels or cache-clear correctness; bounded memory during rapid folder switches and multiple windows.

### 4. Make metadata and decisions cheap on large folders

Keep selected-photo metadata/identity first; add viewport demand before the remainder. Under filename sort with hidden EXIF labels, bulk EXIF indexing can yield or pause; choosing an EXIF sort explicitly requests completion. Evaluate a versioned, source-stamped local EXIF cache for revisits, with missing-value/time-zone behavior preserved. Decisions still require XMP/replacement/conflict checks; an EXIF cache is not permission to skip them.

Load local decision rows in batches, then reconcile external sidecars in priority order. Avoid blocking a foreground save behind a long import/index operation. Existing `DecisionSaveQueue` serializes saves and provides the termination barrier; any coalescing must keep local changes durable, versioned, undoable and correctly reported. Batch one deliberate group action transaction where safe. Synchronizing latest XMP fields after a local commit is a separate concern from discarding intermediate durable decisions. Preserve malformed/conflicting XMP and original bytes.

`setSort` already sorts off the main actor. Some grouped rating operations and verified-arrival paths still sort/rebuild synchronously. Benchmark their main-thread duration at 10k/40k before adding incremental indexes or reworking natural collation. Capture selection by identity and publish a complete ordered result.

**Acceptance:** faster time to first decision, stable EXIF/rating filters/sorts, bounded UI publication rate, correct replacement/conflict behavior and crash/quit recovery. Keep SQLite FULL durability.

### 5. Reduce ingest bookkeeping and repeated source-card reads

**Strong code-backed scaling candidate.** Ordinary `MediaOperations.ingest` rewrites two growing durable JSON manifests after every file. At roughly fixed record size, cumulative encoded records grow quadratically with file count. `ReviewedIngest` already uses durable append-only events and materializes manifests at the end. Evaluate sharing that journal/recovery approach with ordinary ingest, including a schema/migration plan and interrupted-tail recovery. Do not remove durable progress records.

For a newly copied file, current ordinary ingest hashes the source, reads it again for primary copying, and again for backup copying, then verifies each destination. That is three source reads plus two destination verification reads. Prototype reading the source once into bounded chunks, updating SHA-256 and writing two temporary destinations; independently re-read/verify each destination after synchronization. The final source hash must become durable in the journal before publication/acknowledgement. Preserve source fingerprints before/after, no-overwrite rules, cancellation, partial-file cleanup, source protection and per-family metadata/receipt ordering. Existing-target/resume paths need separate treatment; no headline speed claim follows from read counts alone.

Different physical volumes may benefit from overlapping destination writes; a shared device may suffer. Benchmark slow-card + fast SSDs, destinations sharing a device and a slow backup. Keep a family unavailable for ordinary editing until existing verification/receipt rules are met. Prioritize urgent selected families at job preparation; once frozen, changing scope requires a new explicit plan.

**Acceptance:** fewer source bytes read and less journal serialization, earlier verified arrivals and improved copy throughput while culling stays responsive. Fault-inject disk-full, unplug, cancellation, source changes and crashes at every publication boundary. Never replace read-back verification with a hash of the write buffer.

### 6. Reduce gestures and repeat focus processing

Add an optional **Keep focus position** setting for burst review: retain normalized location/magnification across next/previous without immediately starting full RAW work for photos the user skips. Preserve existing default Fit behavior until native trials establish a clear interaction. Offer a temporary point-based loupe and retain comparison lock semantics, shortcut discoverability and navigator accuracy.

Photo already renders an early full-quality RAW focus patch and then the whole image. That patch can still require full RAW processing. Measure patch-only deliberate inspection and retaining the current detail image when toggling Fit/100% under a strict memory budget before pre-rendering neighbors. Do not claim true RAW region decoding.

Some cameras store larger JPEG previews than the current selected embedded thumbnail. Investigate extracting the best available preview for supported camera modes. A sensor-sized embedded JPEG may support a fast camera-preview pixel view, but it is camera-processed, not rendered RAW. Smaller previews must never be enlarged and labelled sensor-resolution 100%. Keep source/resolution visible; do not silently trade focus/exposure fidelity for speed. GPU/Metal rewrites, draft demosaic and replacing ImageIO with libjpeg-turbo remain gated experiments, not recommended first changes.

**Acceptance:** shorter request-to-useful-focus time and fewer gestures, correct Retina/orientation/crop mapping, no stale detail, explicit preview quality/source, preserved current limits and measured peak RSS.

### 7. Shorten the workflow to publication or editor handoff

For deadline work, add user-confirmed camera-locked/photo-pick priority, job presets that combine destination/naming/selected IPTC fields, and caption code replacements. Camera lock semantics need camera/card testing; they are a hint, not Photo's pick flag or consent to delete. Unknown or ambiguous status stays visible. Preserve RAW+JPEG/sidecar family handling.

For large shoots, consider reversible time/camera-based burst grouping with a representative and manual expansion, unreviewed/picks/rejects review scopes and optional focus-position retention. Grouping must not auto-reject or hide unreviewed images permanently. Clock offsets and subsecond capture times matter. Avoid an AI-analysis requirement before the first photo becomes usable.

A prepared ingest job could name destination files and apply explicit metadata templates directly, avoiding a second full batch rename and repeated setup. This requires collision preview, frozen sequence allocation, resume mapping, per-field merge and provenance; never rename a protected source card. Existing separate rename/metadata tools remain useful.

Genuine watched-folder ingest would add file-stability detection and reconciliation for dropped/duplicated filesystem events; current verified arrivals do not implement it. It is valuable for tethered/wire workflows after the core scheduler and copy journal are trustworthy. Publication rendering/composition export and network delivery remain separate product work; Photo-local crops currently do not become rendered delivery edits.

**Acceptance:** measure operator steps and time to first correct deliverable, including caption/name correctness and actual Lightroom/editor read-back. Faster copying alone is insufficient if the operator still repeats setup or sends incorrect metadata.

## Two recommended photographer workflows

| Deadline / wire | Wedding / large shoot |
| --- | --- |
| Open the card in protected review; inspect likely keepers with keyboard + point zoom. | Start verified copying to fast local working storage and a backup; cull verified arrivals while copying. |
| Pick a small urgent set; prepare selective copying, names and essential caption/copyright fields. | First pass rejects technical failures; second pass compares bursts and rates keepers. |
| Work on verified copies; caption only selected fields and prepare the urgent delivery set first. | Apply shared metadata by field to groups; finalize naming/keeper scope before editor handoff. |
| Copy remaining work later if wanted; preserve the source. | Hand keepers to Lightroom/another editor. Protected pre-copy review remains an alternative when it saves enough transfer time. |

The best route depends on source speed, selection ratio, source protection needs and whether copying can overlap review. Pre-copy culling is not automatically fastest for every shoot. The combined naming/template/locked-first conveniences above are proposals, not current single-job behavior; see [USAGE.md](USAGE.md) and [WORKFLOW.md](WORKFLOW.md) for implemented steps.

## Measurement and release gates

Build a repeatable, licensed/synthetic mixed-camera corpus plus optional personal-reference runs kept outside Git. Use 115, 2k, 10k and 40k items; JPEG, Sony/Canon/Olympus RAW, varied preview sizes/orientation, corrupt files, missing metadata and replacements. Test cold/warm/relaunch, sequential/reverse/random navigation, range/marquee/batch decisions, EXIF/rating sorts and active two-destination copying. Include an 8/16 GiB-class Mac and local SSD, card/external drive and network storage where available.

Record p50/p95/p99 and sample counts for interaction/queue/decode/save/detail/copy stages; frame hitches at the display's actual refresh rate; peak RSS and decoded/backlog/cache bytes; source/destination I/O, hit rate and discarded speculative jobs. Separate time to first preview from time to first decision and local-save acknowledgement from XMP completion. Report total ingest time and time to first verified deliverable together. Repeat paired release runs; do not flush or describe OS caches inaccurately.

Proposed initial interaction goals, to ratify against baseline: input-to-local visual feedback p95 under 50 ms; ordinary main-thread update work usually under 5 ms; warm next-photo presentation p95 under 100 ms. These are experiment goals, not achieved guarantees or portable deadlines. Retain existing camera-specific service targets and report cold RAW detail separately. A change should not improve throughput by making foreground latency materially worse; compare concurrent-ingest latency and throughput on the same devices.

No original-byte/sidecar loss, mislabeled low-resolution focus, skipped decisions, moved selections, weakened durability or unverified publication is an acceptable optimization. Ship each measured chunk independently. Prototype AppKit recycling or another decoder only if profiling still identifies grid/view lifetime or decode CPU as the limiting factor after the smaller changes.

## Recommended next chunk

Implement local performance signposts and an end-to-end release scenario harness, then reduce metadata/decision UI publication overhead where traces confirm it. That establishes trustworthy baselines for the foreground scheduler. Follow with bounded nearby Fit preparation and deferred thumbnail-cache writes; prioritize the ordinary-ingest journal next for large shoots. Keep focus/workflow additions separately reviewable and keep the benchmark/handoff updated with every measured result.
