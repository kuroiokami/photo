# Performance lessons from RAWviewer, RawSpeed and Geeqie

Reviewed: 2026-10-26. Photo baseline: `c7318205b9b5fc3c3a91db5c5eb79dde47971b22`.

This is a source review and ranked experiment plan. **No runtime optimizations or new dependencies are implemented here.** None of these applications/libraries was built, executed or benchmarked for this review. Their performance claims are not measurements of Photo. Rapid full-contact-sheet lag remains unresolved; the [row-layout trial](decisions/0034-contact-sheet-row-experiment.md) was withdrawn because it did not establish a reliable benefit.

## RAWviewer: constrain the gallery's work

- **Reuse cells and cache geometry.** `JustifiedGallery` keeps layout records, finds the visible range by binary search, and returns offscreen widgets to a pool. For Photo, evaluate `NSCollectionView` with reusable cells and layout work tied to inventory, width or density changes. Replacing `LazyVGrid` with lazy rows alone did not test this cell-lifetime design. [Layout and viewport lookup](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/gallery_view.py#L3303-L3327), [widget recycling](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/gallery_view.py#L3499-L3510).
- **Keep cells inexpensive without losing culling controls.** Its basic tile is a label with rating/edit badges. Photo requires directly clickable stars/flags, group actions and rotate/crop controls. Test lightweight native cells with those controls and accessibility intact; wrapping the entire existing SwiftUI hierarchy in reusable hosting views may retain layout/focus costs. That last point is a hypothesis, not a measured result. [Thumbnail widget](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/widgets.py#L25-L54).
- **Budget UI publication.** Completed thumbnails are coalesced and drained in bounded batches; defaults are eight per event-loop tick, reduced during fast scrolling. Photo could apply grid completions under a small measured main-thread budget while publishing the selected preview immediately. Preserve session/identity checks and ensure fast scrolling never leaves visible tiles permanently blank. Do not copy fixed batch sizes or timer intervals without display/frame measurements. [Completion drain](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/gallery_view.py#L4454-L4480).
- **Retarget queued loads.** Queued work is reprioritized against the viewport; distant queued thumbnails can be dropped. Interactive single-image work has a separate pool from gallery work. Photo already has separate thumbnail/Fit/detail lanes; add viewport demand to thumbnail scheduling and test a small bounded worker pool for cold tiles. A running synchronous decode may remain uninterruptible. [Queue policy](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/image_load_manager.py#L1819-L1884), [pool selection](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/image_load_manager.py#L1055-L1072).
- **Decode an adequate embedded preview.** The TIFF-based path selects the smallest embedded JPEG covering the requested long edge; full-quality requests select the largest. Audit Photo's ImageIO/camera-specific paths before adding extraction logic: a small output does not by itself prove which source preview was used. Keep Retina sizing, orientation and source labels correct. [Preview selection](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/enhanced_raw_processor.py#L550-L579).
- **Reuse the right cached representation.** It caches fitted tile images by physical size/rotation and prunes local gallery entries to retained paths. Photo can test reusing unchanged decoded thumbnails across reloads and overlapping parent/subfolder scopes; its RAM cache currently resets per session. Reuse needs source identity/fingerprint invalidation, not simply removal of the session reset. [Fitted cache keys](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/gallery_view.py#L1761-L1799), [retained-path pruning](https://github.com/markyip/RAWviewer/blob/4365f56a98d65fdf66a3546e7b777ad40a4ce0a3/src/rawviewer_ui/gallery_view.py#L1417-L1444).

## Geeqie: prioritize the visible working set

- **Reusable interactive item lifecycle.** Its GTK grid uses factory setup/bind/unbind. Setup creates picture, label and mark controls; bind connects the current item, while unbind disconnects it and drops the displayed texture. This is a useful model for reusable cells that preserve Photo's controls. Bind identity, cancellation and stale-result rejection must follow the new photo when a cell is reused. [Cell factory](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/view-file/view-file-icon.cc#L1716-L1780).
- **Bound work to the viewport.** Its thumbnail state builds a position index when the model changes. A viewport update queues visible photos, then roughly one viewport on either side, nearest first; it explicitly avoids continuing through the whole directory after that queue. Low-priority idle scheduling coalesces repeated requests. Adapt the policy to Photo's filtered/paired/recursive visible order; do not scan all 40k files on every scroll. [Thumbnail queue](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/view-file/view-file-thumbnail.cc#L23-L166).
- **Protect active images within a measured memory policy.** Its shared resident thumbnail cache protects visible files and active loads across panes. Its source explicitly allows those protected entries to exceed the configured budget temporarily. Borrow the working-set policy, not an unbounded exemption: Photo needs explicit multi-window/active-image memory accounting, pressure handling and separate RSS reporting. Keep Photo's existing constant-time LRU/accounting strengths. [Resident cache](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/view-file/view-file-thumbnail.cc#L36-L88).
- **Start read-ahead after the current image.** `image_read_ahead_start` waits while the foreground loader exists. Its deferred loader lets superseding input cancel work before metadata reading; a 120 ms timer is specific to one external-selection path, not a universal navigation delay. Photo already bypasses its short cold-Fit debounce for RAM hits. Test bounded adjacent Fit-preview preparation after the current preview is ready; preserve immediate cached navigation and avoid speculative full RAW detail. [Read-ahead](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/image.cc#L983-L1018), [deferred start](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/image-load.cc#L1253-L1280).
- **Choose preview/decode size early.** It requests embedded previews through Exiv2/LibRaw and uses JPEG decoder scaling rather than always allocating full-sized output. Exact preview selection depends on the compiled metadata backend; the fallback EXIF implementation differs. Photo already uses embedded previews and ImageIO downsampling. Measure any remaining source-selection or repeated-parse cost before replacing those paths. [Source setup](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/image-load.cc#L932-L980), [JPEG scaling](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/image-load-jpeg.cc#L340-L354).
- **Separate first paint from refinement.** Its renderer has first-pass and second-pass tile queues. This suggests testing cheap presentation during movement followed by refinement after settling, only where it improves measured latency. Keep genuine 100% inspection/source labels truthful. Tiled output rendering does not prove that full RAW unpacking/demosaicing was avoided. [Two-pass renderer](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/src/renderer-tiles.cc#L1498-L1576).
- **Validate cached files, not just paths.** Its thumbnail documentation describes replacement/change detection using identity and timestamps, plus size validation for shared thumbnails, and acknowledges cases it cannot detect. Preserve Photo's source-change, orientation and replacement protections when extending reuse. [Thumbnail cache documentation](https://github.com/BestImageViewer/geeqie/blob/85f03d6d59f8464464d8b720dc33dbf2ce3bf4b6/doc/docbook/GuideReferenceThumbnails.xml).

## RawSpeed: useful decoder engineering, a different pipeline stage

RawSpeed supplies sensor data and camera/CFA information. It does **not** demosaic, apply display color/white balance, or provide a viewable thumbnail. It is not a drop-in replacement for Photo's embedded-preview browsing or complete Apple RAW-rendering path. Integrating it alone would not resolve warm JPEG contact-sheet layout lag. [Project scope](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/README.rst).

- **Use bounded views instead of repeated small allocations.** Its non-owning `Buffer`/`ByteStream` abstractions expose checked subviews over existing bytes. This informs the open Photo CR3 buffered-reader experiment: reduce tiny seek/read calls and temporary integer arrays while retaining bounds, overflow, orientation, cancellation and fallback checks. Its provided `FileReader` reads a complete input into an aligned allocation; do not adopt whole-file reads merely to find an embedded thumbnail. [Buffer](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/librawspeed/io/Buffer.h), [FileReader](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/librawspeed/io/FileReader.cpp#L47-L142).
- **Parallelize independent decode regions within an application-wide budget.** The Sony ARW2 decompressor processes rows with OpenMP and a caller-supplied thread count. This is evidence of a decoding design, not a speed prediction for Apple's opaque decoder. If a custom detail backend is ever justified, coordinate per-image threading with concurrent photos/metadata/ingest to avoid oversubscription. Some optimized paths are SSE2-specific and cannot be assumed to benefit Apple silicon. [Sony row decoder](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/librawspeed/decompressors/SonyArw2Decompressor.cpp#L55-L144), [platform-specific scaling](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/librawspeed/common/RawImageDataU16.cpp#L186-L207).
- **Reuse immutable decoder setup.** Camera definitions can be retained across files; this is different from reusing file-specific EXIF or XMP without invalidation. Keep decoder setup separate from source-stamped metadata caches. [Decoder API guide](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/librawspeed/README.md).
- **Benchmark stages and scaling honestly.** `rsbench` reports CPU and wall time and varies decoder thread count. Its input `Entry` retains file contents after the first load, and camera definitions are static, so results cannot be treated as cold-card I/O, a rendered color preview, or scroll frame times. Report inventory/read/extraction/unpack/render/publication/presentation separately. [Benchmark input and loop](https://github.com/darktable-org/rawspeed/blob/0c16fee7772594e98897bded01fc31bc3409b4cb/src/utilities/rsbench/main.cpp#L110-L188).

## Ranked Photo experiments

| Order | Proposed work | Evidence needed before acceptance |
| --- | --- | --- |
| 1 | Native reusable interactive contact-sheet cells; stable layout/position index independent of scrolling and unrelated state. | Warm fully cached scrolling improves; visible/buffered cell counts remain bounded; keyboard reveal, reflow, marquee, direct stars/flags, group edits, filters and accessibility pass. |
| 2 | Time-budgeted grid completion publication, visible-first queues and small bounded thumbnail workers. | Cold viewport fill and input response improve under rapid/reverse/jump scrolling; no blank-tile starvation, stale cells or selected-preview regression. |
| 3 | Nearby Fit read-ahead only after foreground readiness, yielding to navigation and verified ingest. | Sequential/reverse navigation improves without wasted RAW detail, source-card contention or excessive RSS. |
| 4 | Source-stamped cache reuse for overlapping scopes/reloads, optional fitted-size representations and visible working-set protection. | Revisit gains; replacement/orientation/clear-cache/multi-window/pressure checks; include all retained views/textures outside cache counters. |
| 5 | Bounded buffered CR3 parsing and camera-specific embedded-preview selection audit. | Fewer reads/allocations and lower cold-thumbnail latency on actual camera fixtures, with malformed/cancel/fallback/source-hash checks intact. |
| Later | Alternative RAW unpack/render backend. | Demonstrated end-to-end genuine-detail bottleneck, supported-camera/color/orientation parity, memory/thread/build feasibility and full rendering integration. No library selected. |

These are proposals, not completed checklist items. Photo already has embedded-only browsing, ImageIO downsampling, separate thumbnail/Fit/detail lanes, bounded RAM/disk caches, RAM-only immediate lookups, background optional cache writes and per-photo observation. Preserve them instead of reimplementing them from another project.

Use a small deadline-oriented shoot and 115-JPEG warm/cold controls, then distributed 2k/10k collections, with 40k as a stress case. Separate first-open, same-session revisit, reload/scope change and memory-pressure results. Include real RAW/EXIF diversity and concurrent verified ingest. Record exact release binary, display/window/density, input sequence, cache state, original hashes, RSS and usable frame/hitch/input latency. Scripted accessibility overhead, decoder microbenchmarks and completed scroll commands do not establish physical-trackpad smoothness or parity with another app.
